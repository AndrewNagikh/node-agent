# Task 24 churn test — first live run, 2026-07-28

Cluster: node-a (192.168.50.42, this machine), node-b (.254), node-c (.51),
orchestrator on .154. 13 installed models, 522 blobs tracked.

## Outcome

Steps 1–3 of the acceptance test pass, **after eight defects that only a live
run could expose** (table below). Steps 4–6 skipped by decision.

Final state, verified end to end: with node-a stopped, coverage reads
UNAVAILABLE with `missing=0` and install plans are empty -- no downloads and
no deletions. On its return all 13 models are READY in ~20-45s with no manual
action, layouts unchanged and no blob moved.

The safety property held from the very first run and never broke: **no blob
was ever deleted, no layout ever changed, zero bytes ever moved.** Every one
of the eight defects was about the orchestrator's *picture* of the cluster,
not its treatment of the data -- though #7 and #8 were one button-press away
from changing that.

## A correction worth recording

The first run appeared to pass: 12 of 13 models "returned to READY on their
own" after node-a came back. That reading was wrong, and the harness could
not catch it, because it compared against a snapshot whose READY values were
themselves stale.

Nothing had recovered. Those models were simply never re-polled while node-a
was down, so an old READY survived untouched. The one model that *was*
re-polled during the outage (`gemma-3-1b`, refreshed by hand) went DEGRADED
and stayed DEGRADED.

The experiment that settled it: with node-a stopped, force a coverage refresh
on **every** model, so every record is honest. That left 10 DEGRADED and 3
READY (the 3 place no layers on node-a). Then start node-a and touch nothing.

- **Before the fixes:** node-a healthy for several minutes, all 10 still
  DEGRADED. Not one recovered. Each needed a manual refresh.
- **After the fixes:** all 13 READY by the first poll after registration,
  no manual action, and `churn_check.py verify` PASS — layouts unchanged, no
  blob lost or moved.

"Zero manual intervention" was failing completely, and the failure was
invisible until every coverage record was forced to be current.

## Defect 1 — no liveness detection at all

`online` was set true on registration and never set false anywhere in the
tree. `last_seen` was recorded and read by nothing. A stopped node stayed
"online" until the orchestrator itself restarted; node-a was still listed
online two minutes after being killed.

Consequences: coverage polls kept going to a machine that was not there and
came back with its layers marked missing, so healthy models read DEGRADED.
`gemma-3-1b` showed 15/26 while all 28 of its blobs sat on node-a's disk —
verified byte-for-byte against what the harness called lost:

| model | harness "lost" | actually on disk |
|---|---|---|
| llama-3.3-70b-q3ks | 30 blobs, 10307.5 MB | 30 blobs, 10308 MB |
| qwen3-30b | 13 blobs, 4586.7 MB | 4587 MB |
| tinyllama-1.1b | 4 blobs, 100.5 MB | 4 blobs, 101 MB |
| smollm2-1.7b | 5 blobs, 238.3 MB | 5 blobs, 239 MB |

It also made `layout_policy`'s `unavailable` verdict unreachable: the branch
written specifically to protect an absent node's layers could never be taken,
because no node was ever absent.

Fixed in `5b51916a4` — `node_is_online()` derives liveness from `last_seen`
(node_agent re-registers every 5s; 30s of silence counts as gone). Measured
live: node marked offline 15–30s after the process dies.

## Defect 2 — a returning node was not a membership change

`cluster_changed` was true only for a node absent from `g_nodes`, or a ≥5%
score / ≥10% memory change. Nothing ever erases `g_nodes` entries, so a
machine that left and came back kept its entry and its score, matched no
threshold, and was handled as an ordinary heartbeat. No bootstrap, no
re-poll — so coverage never healed, and whatever was recorded during the
absence stayed on the record indefinitely.

Fixed in `8da5daa21`. The condition is only expressible once defect 1 is
fixed: before that a node was never offline, so there was no return to
notice.

Re-polling on return is safe to do eagerly because `decide_layout_action()`
governs what may be done to a layout — it keeps or repairs, and recomputes
only when there is no runnable layout left to protect.

## The full list: one mistake in eight places

Every defect below is the same error -- **unreachable read as absent** --
and each was only exposed by fixing the one before it. Worth recording as a
list, because the shape repeated far past the point where it looked finished.

| # | Where | Symptom |
|---|---|---|
| 1 | `online` flag | never set false; a stopped node stayed online forever, making `unavailable` unreachable |
| 2 | returning node | `g_nodes` entries never erased, so a return was an ordinary heartbeat -- no resync, coverage never healed |
| 3 | `compute_coverage` | offline node's layers counted as `missing`, so a closed laptop read as data loss |
| 4 | `apply_actual` | a poll that missed a node erased its layers from the registry |
| 5 | `build_and_store_install_plan` | passed the planner the raw poll instead of the merged record |
| 6 | `compute_runtime_coverage` | offline node never in `targets`, so its blobs read as misplaced -> DEGRADED |
| 7 | `build_install_plan` | no liveness at all; empty `online_nodes` means "assume all up" |
| 8 | plan deletions | 291 DELETEs against b/c while node-a was invisible |

On #8: those deletes turned out to be **entirely spurious**, not legitimate
cleanup deferred to a better moment. With the cluster whole the plan is 0
operations -- had they been real leftovers, they would still be pending. They
came from a runtime node map computed over an incomplete cluster. The guard
was right, for a stronger reason than the one it was written for.

## Still open

- Acceptance steps 4-6 skipped by decision (2026-07-28): node-a exercised the
  same code paths, and the three-node assumption was already removed from the
  tooling. Multi-day unattended operation remains unproven by construction --
  it needs days.
- **Latent:** an empty `online_nodes` means "assume every node is up". Tests
  rely on it, and it is what let #7 through. The runtime exposure is a poll
  that reaches *nobody*: every node then reads online and every layer missing.
  Nothing destructive follows today (the layout policy takes its online set
  from `g_nodes`, not the poll), but a caller deriving liveness from a poll
  must treat "nobody answered" as "we know nothing".
